## message เป็นมากกว่า body

ตอน publish ตัว body — bytes จริง ๆ — เป็นแค่ครึ่งเดียวของเรื่อง ทุก AMQP message ยังพก **properties** มาด้วย: metadata ที่ RabbitMQ และ consumer ของคุณเอาไปใช้ได้โดยไม่ต้อง parse body บางตัวเป็นแค่ข้อมูลประกอบ แต่มีสองสามตัวที่เปลี่ยนพฤติกรรมการ deliver จริง ๆ

## property ที่เปลี่ยนพฤติกรรม: `delivery_mode`

property เดียวที่มีผลต่อ reliability คือ **`delivery_mode`** (หรือเรียกว่า "persistent"):

- `delivery_mode = 2` (**persistent**) — RabbitMQ เขียน message ลง disk มันจึงรอดจากการ restart broker ได้
- `delivery_mode = 1` (**transient**, ค่า default ใน AMQP ดิบ ๆ) — message อยู่ใน memory และหายเมื่อ restart

จับคู่มันกับ durable queue (บทเรียนที่แล้ว) กฎนี้ควรจำ: **durable queue + persistent message = รอดจากการ restart** ขาดครึ่งใดครึ่งหนึ่งข้อมูลก็เสี่ยง

persistence ไม่ฟรี — การเขียนลง disk กิน throughput นี่คือ trade-off จริงที่คุณจะชั่งน้ำหนักในโมดูล reliability

## property ที่เป็นข้อมูลประกอบ

ที่เหลืออธิบาย message เพื่อให้ consumer (และเครื่องมือต่าง ๆ) จัดการมันได้ถูกต้อง:

| Property | จุดประสงค์ |
|----------|---------|
| `content_type` | เช่น `application/json` — จะตีความ body อย่างไร |
| `content_encoding` | เช่น `gzip` |
| `headers` | metadata key/value อิสระ (ใช้โดย headers exchange ด้วย) |
| `correlation_id` | จับคู่ reply กับ request ของมัน (pattern RPC) |
| `reply_to` | queue ที่ควรส่ง reply ไป |
| `message_id` | id เฉพาะตัว — มีประโยชน์สำหรับ idempotency และ deduplication |
| `timestamp` | เวลาที่ message ถูกสร้าง |
| `priority` | message priority สูงกว่าแซงคิว (ต้องใช้ priority queue) |
| `expiration` | TTL ต่อ message เป็นมิลลิวินาที |

## publish พร้อม properties

<Tabs syncKey="lang">
  <TabItem label="Node">
    ```js
    channel.publish('orders', 'order.created', Buffer.from(JSON.stringify(order)), {
      persistent: true,          // delivery_mode = 2
      contentType: 'application/json',
      messageId: order.id,
      timestamp: Date.now(),
      headers: { source: 'checkout' },
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    channel.basic_publish(
        exchange="orders",
        routing_key="order.created",
        body=json.dumps(order),
        properties=pika.BasicProperties(
            delivery_mode=2,               # persistent
            content_type="application/json",
            message_id=order["id"],
            headers={"source": "checkout"},
        ),
    )
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    ch.PublishWithContext(ctx, "orders", "order.created", false, false,
        amqp.Publishing{
            DeliveryMode: amqp.Persistent, // delivery_mode = 2
            ContentType:  "application/json",
            MessageId:    order.ID,
            Timestamp:    time.Now(),
            Headers:      amqp.Table{"source": "checkout"},
            Body:         body,
        },
    )
    ```
  </TabItem>
</Tabs>

<Callout title="สรุปหนึ่งบรรทัด">
message พก body บวก properties property ส่วนใหญ่เป็นข้อมูลประกอบ (`content_type`, `message_id`, `headers`, `correlation_id`) แต่ **`delivery_mode`/persistent** คือตัวที่สำคัญต่อ reliability: เมื่อรวมกับ durable queue มันคือสิ่งที่ทำให้ message รอดจากการ restart broker ได้ — โดยแลกกับการเขียน disk ทุกครั้งที่ publish
</Callout>
