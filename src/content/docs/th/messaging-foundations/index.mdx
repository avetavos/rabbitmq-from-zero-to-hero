## ไอเดียในประโยคเดียว

**RabbitMQ คือ message broker: infrastructure ที่วางอยู่ตรงกลางระหว่าง service ที่ *ผลิต* งาน กับ service ที่ *ทำ* งาน เพื่อให้สองฝั่งไม่ต้องคุยกันตรง ๆ** producer โยน message เข้า RabbitMQ แล้วไปทำอย่างอื่นต่อ ส่วน consumer ก็หยิบไปทำเมื่อพร้อม

การมีตัวกลางคั่นตรงนี้ — buffer ตรงกลาง — คือหัวใจทั้งหมด ทำให้ระบบรับมือกับ spike ได้, ทนต่อการที่ consumer ล่ม และ scale สองฝั่งแยกจากกันได้

## ทำไมต้องเริ่มที่นี่

เกือบทุก feature ของ RabbitMQ — exchange, acknowledgement, dead-letter queue, confirm — ล้วนเป็นการต่อยอดจาก flow ง่าย ๆ อันเดียว จำภาพนี้ไว้ในหัวก่อน:

export const shapeDiagram = `flowchart LR
  prod["Producer\n(ส่งงาน)"] -->|publish| ex["Exchange\n(route)"]
  ex -->|binding| q["Queue\n(buffer)"]
  q -->|deliver| cons["Consumer\n(ทำงาน)"]`;

producer publish ไปที่ **exchange** จากนั้น exchange route message ไปยัง **queue** หนึ่งตัวหรือหลายตัว แล้ว consumer อ่านจาก queue เหล่านั้น producer ไม่เคยรู้เลยว่าใครเป็นคน consume, เมื่อไร หรือมี consumer กี่ตัว ทุกอย่างที่ตามมาคือเรื่องของการควบคุมและทำให้ flow นี้แข็งแรงขึ้น

<Callout title="การเปลี่ยนมุมมอง">
call แบบ synchronous (HTTP, gRPC) คือการถามคำถามแล้ว **รอคำตอบ** — ฝั่งที่เรียกถูก block และฝั่งที่ถูกเรียกต้องออนไลน์อยู่ตอนนั้น ส่วน messaging คือ **fire-and-forget**: คุณส่งงานให้ broker แล้วไปทำอย่างอื่นต่อ งานจะถูกทำในภายหลังโดยใครก็ตามที่ฟังอยู่ คนละเครื่องมือ คนละการรับประกัน — และที่เหลือของคอร์สนี้ก็ว่าด้วยการรับประกันเหล่านั้น
</Callout>
